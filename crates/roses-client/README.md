# Native opening client

`roses-client` presents an imported opening movie, observed title/menu screens and imported story pages in a Windows window. It starts no emulator. The stage graph, labels, atlas crops, layout, colours, timing and optional WAV music come from a private import manifest. No game assets or original dialogue are bundled in this crate. Unsupported menu branches and story boundaries show a separate implementation-status dialog; they do not pretend to continue into an unimplemented scene or native duel.

```powershell
cargo +1.92.0 build --release -p roses-client --offline
.\target\release\roses-client.exe --manifest .\private-import\manifest.json --check
.\target\release\roses-client.exe --manifest .\private-import\manifest.json
```

Without arguments, the executable looks for `roses-data/opening/manifest.json` beside itself. A clean checkout has no imported assets. `--check` validates without opening a window, decoding video, or asserting visual/audio equivalence. `--fullscreen` starts borderless fullscreen; F11 toggles it and restores the prior window placement. Resize preserves the manifest's explicit display aspect. Video fills that same aspect rectangle, so decoded square-pixel dimensions cannot silently replace the observed PS2 display aspect.

Keyboard: arrows navigate, X is Cross, Z/Escape is Circle, S is Start, Enter invokes the current stage's first configured confirmation/advance/skip button. Alt+F4 closes. XInput: A is Cross, B is Circle, Start is Start, and D-pad/left stick navigate. Directions act on new presses; holding does not repeat. Input-repeat timing and all controller hardware have not been matched to the original. The manifest controls boundary wrapping and whether Circle has any action.

The `roses-opening-1` JSON schema is represented by public types in `src/lib.rs`; unknown fields are rejected. It contains:

- `source`: profile `dotr-europe-sles-51579`, disc SHA256 and executable SHA256. These are caller-provided identity metadata, not authentication of the source game.
- `canvas`: logical `width`, `height`, plus independent `aspect_width`, `aspect_height`.
- `assets`: unique `id`, `kind` (`png`, `video`, `wav`), relative child `path`, exact `bytes`, SHA256. The loader checks all assets, canonical containment, sizes, image dimensions and decoded-image budget before displaying anything. Hashes detect mismatches against this manifest; they do not establish an authorized distribution or truthful provenance.
- `initial_stage` and `stages`: explicit movie, screen and menu states. No stage order or timing is inferred from filenames.

Each `Layer` has `asset`, optional crop `source:[x,y,width,height]`, canvas `destination:[x,y,width,height]`, optional `tint:[r,g,b]` (default white), `opacity` (default255), `flip_x` (default false), and `filter` (`linear` by default or `nearest`). Both rectangles must fit their image/canvas; rendering does not silently clip. Linear sampling blends premultiplied alpha and clamps within the chosen crop to prevent neighboring atlas sprites bleeding in. Multiple cropped layers can form a frame; there is no guessed original frame sprite or generated original artwork.

`movie` stages name a video asset and `on_end` target. Optional `skip_buttons` and `on_skip` must be supplied together. `screen` stages have layers, `next`, explicit `advance_buttons` and/or an optional `duration_ms` (1..600000). `menu` stages have background layers, imported entry labels, per-entry `normal_layers`/`selected_layers`, an `initial_selection`, `confirm_buttons`, optional `cancel_target`, and `wrap_navigation`. Entry actions are either `{"kind":"unavailable"}` or `{"kind":"stage","target":"observed-stage-id"}`. Screens and menus may have `music:{"asset":"wav-id","looped":true}`. Timing, skip behaviour and targets should only be populated from observations; missing original behaviour is not evidence of parity.

`story` stages contain `id`, `pages:[{"id":"page-id","layers":[...]}]`, optional `music`, explicit `advance_buttons`, and `on_end`. There must be1..64 pages with unique IDs and nonempty bounded layer lists. A new advance-button press repaints the next page and retains the same audio playback. Entering the story again resets to its first page. At the final page, `on_end:{"kind":"stage","target":"observed-stage-id"}` transitions to another implemented stage; `on_end:{"kind":"unsupported","message":"..."}` shows the supplied implementation-status text and retains the last original page. Any original page marker must come from imported layers; the client adds no page counter to the game canvas. This first page model shows complete imported pages. Text reveal animation and its input timing remain unimplemented until supported by reference observations.

`deck_choice` (starter-deck select, candidates from the committed name) and `placeholder` (explicit stand-in for an untraced segment, no original art) stages carry untraced parts as text: `Model::explicit_status()` returns the stand-in message or the three candidates with the current selection, and this client draws it in white in the frame's top band (canvas rows 0..116, black here), so it stays visible in fullscreen. Left/Right change the deck, S (Start) confirms; X continues a stand-in.

Native video uses Windows Media Foundation's MFPlay API and installed Windows codecs; H.264/AAC MP4 is the current import target. MFPlay is a legacy API, chosen here for a small native opening slice; it is not the planned renderer for 3D duels. COM callbacks only enqueue generation-tagged terminal events. The UI owns stage transitions and shuts down the previous player before replacing or destroying its surface. Audio/video files remain open with Windows read sharing only while loaded to prevent path replacement after hash validation. Static PNGs are held as decoded pixels. See [Microsoft's MFPlay guide](https://learn.microsoft.com/en-us/windows/win32/medfound/getting-started-with-mfplay) for the playback, callback and paint contracts.

Music may additionally specify `loop_start_frame`, for example `{"asset":"music","looped":true,"loop_start_frame":827456}`. The position counts sample frames (one sample per channel), and must precede the WAV's end. The client plays frames before that position once, then repeats the remaining frames using queued waveOut buffers. A zero position loops the whole PCM stream. The position requires `looped:true`; omitting it retains the existing PlaySound whole-file behavior. Loop-region WAVs are hash-checked and parsed before any window opens: RIFF/chunk sizes, PCM16 mono/stereo format, sample rate8..192kHz, byte rate, block alignment, nonempty complete sample frames and loop bounds are checked. Their combined file budget is128MiB. Unknown ancillary chunks are skipped with bounds and padding checks; duplicate format/data chunks are rejected. The parser does not infer timing or read `smpl` loop metadata.

The waveOut backend owns stable PCM and header allocations until reset, unprepare and close complete. It queues the intro and loop while paused, then starts them together; the loop count is `u32::MAX`. Advancing a story page only repaints and does not restart playback. Stage changes and closing stop it. An exceptional audio-driver cleanup error retains the allocations to avoid freeing memory still referenced by the driver. Windows may apply device mixing/resampling; audible output, loop continuity on hardware and original mixer parity require separate runtime checks. The queue follows Microsoft's [WAVEHDR loop contract](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/ns-mmeapi-wavehdr) and [header preparation contract](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/nf-mmeapi-waveoutprepareheader).

The media boundary converts canonical Windows verbatim drive/UNC paths to ordinary drive/UNC spelling because MFPlay's URL resolver otherwise reports a network-path error for a local file. Validation and read locks keep the canonical path. Relative paths and device namespaces are rejected at that boundary. Creating the player is asynchronous: aspect configuration waits for the successful `PLAY` callback and is applied on the UI thread, rather than prematurely after creation. A best-effort `roses-client.log` beside the executable records startup, stage changes, media events, errors and Rust panic backtraces; it stops appending once about4MiB is reached. Window-handler panics are caught before crossing the native ABI and cause orderly failure. Native codec/driver crashes still require Windows crash diagnostics.

Synthetic tests cover stage transitions, explicit timers, unavailable branches, bounds and hash rejection, crop validation, compositing and aspect fit. These tests do not establish original-game playback fidelity, synchronized audio, physical controller compatibility, or completed native gameplay. Those require separate runtime observations.
